Low-rank adaptation

The cost of full fine-tuning

Full fine-tuning updates every weight in the model — which means storing a full copy of the weights (and the optimiser’s own state for each one) for every task you fine-tune for.

  • Fine for a 100M-parameter model. Increasingly painful for a 7B, 70B, … parameter model.
  • If you want ten fine-tuned variants of a large model, full fine-tuning means ten full-sized copies.

We’d like most of the pretrained weights to stay exactly as they are, and only train a small add-on.

Where the memory goes

Full fine-tuning with the Adam optimiser, in 32‑bit floating point, needs for every parameter:

bytes
weight 4
gradient 4
Adam’s two averages 8
total 16
  • SmolLM2-135M: \(135\text{M} \times 16 \text{ bytes} \approx 2.2\text{ GB}\). Fine.
  • SmolLM2-1.7B: \(1.7\text{B} \times 16 \text{ bytes} \approx 27\text{ GB}\), compared with 8 GB on each of our GPUs.
  • On top of this come the activations: values saved during the forward pass for the backward pass, growing with batch size and sequence length.

The same model, with LoRA

Adapters and LoRA

LoRA (Low-Rank Adaptation) freezes the pretrained weight matrix \(W\) entirely, and learns a small update to it instead:

\[W' = W + BA\]

where \(B\) and \(A\) are much smaller matrices whose product \(BA\) approximates the update \(W\) would have needed.

  • \(A\) and \(B\) have an inner dimension \(r\) (the rank) — much smaller than \(W\)’s own dimensions.
  • Trainable parameter count scales with \(r\), not with the size of \(W\): a low rank means very few extra parameters, at some cost in how expressive the update can be.
  • Only \(A\) and \(B\) need storing per task — the shared frozen \(W\) is reused across all of them.

The update as a matrix product

Reading a LoraConfig

from peft import LoraConfig

config = LoraConfig(
    r=8,             # rank of the update
    lora_alpha=32,   # scales the update's contribution
    target_modules=["q_proj", "v_proj"],
)

r is the rank from the formula above; lora_alpha is a scaling factor applied to \(BA\) before it’s added back to \(W\) — together they control how much capacity, and how much influence, the adapter has.

What difference does LoRA make?

  • Frozen weights need no gradient and no optimiser state: of the 16 bytes per parameter, only the weight itself remains.
  • The adapter’s parameters cost the full 16 bytes each, but there are very few of them: 0.34% of SmolLM2-135M at \(r = 8\).
  • The activations are not saved: gradients still have to flow back through the frozen layers to reach the adapters.
  • Storage: SmolLM2-135M’s adapter is about 2 MB on disk, against over 500 MB for a fully fine-tuned copy.

For a small model, LoRA saves much less GPU memory than “0.34%” suggests. You will measure this in the lab.

Quantisation

Quantisation

A separate way to cut memory use: store weights with fewer bits than the usual 32/16-bit floats.

  • int8 or even 4-bit representations pack the same weight into much less memory.
  • Since low-bit integers can’t represent a full floating-point range directly, a scale factor maps the original float range onto the small integer range (and back again when the weight is used).
  • Too aggressive a quantisation loses precision, and accuracy can suffer. The balance between memory and accuracy can be tuned by the number of bits used and the scale factor.

From float to int4 and back

With \(\alpha = 7 / \max|x| = 7/5.4 \approx 1.30\): \(\;1.2 \xrightarrow{\times\alpha} 1.56 \xrightarrow{\text{round}} 2 \xrightarrow{\div\alpha} 1.54\), stored as 0010: 4 bits instead of 32.

Every value moves by at most half a step, \(1/(2\alpha) \approx 0.39\); \(0.3\) is rounded to \(0\) and lost entirely.

Outliers may be a problem

In the example, the single value \(5.4\) sets the step size for all nine numbers, and small values like \(0.3\) are lost.

  • Block-wise scales: give each small block of weights (say 64) its own scale factor, so an outlier only coarsens its own block. The price is one extra number per block.
  • NF4 (“normal float 4”): rather than 16 evenly spaced levels, place them more densely near zero, where most of a trained model’s weights lie.
  • Weights are stored in 4 bits but converted back to 16 bits on the fly for each matrix multiplication: quantisation saves memory, not computation.
